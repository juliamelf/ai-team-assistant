| Время и токены не сохранялись | `app.pipeline_runs`: время распознавания, время ответа модели, токены по каждому запуску; сводка — `app.v_runs_daily` |

## Как переключиться (≈ 20 минут)
 
1. **Обновить базу.** Импортируйте новый `e03_setup_db.workflow.json` вместо старого (или удалите старый), выберите credential в семи узлах Postgres и запустите. Повторный запуск безопасен. В «7. Проверка» должно быть как раньше, плюс `chat_state_exists_true = true`, `prompt_v3_1 = 1`, `audio_table_true = true` и `004_v5_bot, 005_speech_date, 006_audio_pseudo` в `migrations`.
2. **Импортировать v5.** Import from File → `workflow_v5.json`. Появится «MVP · Сценарий A v5 (PostgreSQL + дата встречи)», неактивный.
3. **Credential в 11 узлах Postgres:** «Состояние чата», «Сохранить встречу», «Журнал: распознавание», «Сохранить аудио», «Сбросить ожидание», «Ждать правку», «Ждать дату», «Подтвердить в БД», «Встреча для выжимки», «Сохранить выжимку», «Журнал: выжимка». Выберите «Postgres ИИ-ассистент». Если в n8n только один credential Postgres, он подставится сам при открытии узла.
3а. **Очистка аудио.** Импортируйте `workflow_purge_audio.json` («Очистка аудио встреч (3 месяца)»), выберите credential в узле Postgres и включите. Он работает сам раз в сутки.
4. **Переключить.** Сначала **выключите v4**, потом включите v5. Два активных workflow одновременно опрашивают Telegram и забирают сообщения друг у друга.
5. **Откат:** выключить v5, включить v4. Таблица «Выжимки 1:1» не тронута.

Что посмотреть в базе (узел Postgres → Execute Query в любом workflow):
 
```sql
SELECT tg_message_id, status, meeting_date, meeting_date_source, manager_id, corrections,
       summary_draft IS DISTINCT FROM summary_final AS changed, left(transcript, 60) AS transcript
FROM app.meetings ORDER BY received_at DESC LIMIT 10;
 
SELECT * FROM app.v_runs_daily;      -- запуски, p95 распознавания и модели, токены за день
 
SELECT m.tg_message_id, a.size_bytes, left(a.sha256, 12) AS sha256, a.expires_at::date
FROM app.meeting_audio a JOIN app.meetings m USING (meeting_id) ORDER BY a.stored_at DESC LIMIT 10;   -- аудио
```
 
## Прогоны оценочного набора
 
Начинайте запись с даты из сценария: «Встреча с Иваном Петровым четырнадцатого сентября, один на один…». Бот не будет спрашивать дату 20 раз за батч, а в базе останется `meeting_date_source = speech`. Это выполняет настройку прогона из листа «Правила» в e46: «Дата встречи из сценария передаётся в промпт». Если загружаете аудиофайлы из Drive, можно вместо этого писать «14.09» в подписи (`caption`).
 
Отдельно стоит считать, сколько раз дата из речи распознана неверно: это поле `meeting_date_source = speech` у встреч, где потом нажали «Изменить дату» (источник сменится на `button`).
 
## Ограничения v5
 
- **Дата из речи ищется только в первой фразе про встречу** (первые 3 предложения, 25 слов): число и месяц словами или цифрами, «сегодня / вчера / позавчера», «в понедельник» (ближайший прошедший). Не распознаются, например, «на прошлой неделе» и «в начале месяца» — тогда бот спросит кнопками. Если дата не та, «Изменить дату» доступна до подтверждения выжимки.
- **Нет автоматической даты через 30 минут без ответа.** Встреча ждёт в статусе `awaiting_date`, кнопки остаются рабочими. Автоподстановку даты сообщения с пометкой «не подтверждена» (вариант из «Шаг 2.2») можно добавить отдельным расписанием, если понадобится.
- **Аудио в БД** — только у новых встреч; правки голосом не сохраняются. Копия файла остаётся и на серверах Telegram: её срок хранения от нас не зависит.
- **`asr_ms` включает скачивание файла из Telegram**, а не только работу GigaAM.
- **Ошибка GigaChat (HTTP)** обрабатывается как в v4: запуск падает, встреча остаётся в статусе `transcribed`. Повтор при невалидном JSON появится в v6 вместе со схемой 1.0.
