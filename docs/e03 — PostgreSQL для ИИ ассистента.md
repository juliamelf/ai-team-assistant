## Схема
 
```
app (рабочие данные)                                  pii (ПДн отдельно)
├─ employees ─────────────┐ D04 без ФИО               ├─ employee_names    D04 ФИО, короткие варианты
├─ skills, skill_aliases  │ D05                        └─ employee_aliases  D04 все формы имён
├─ skill_levels           │ D06 снимки уровней
├─ sprints, calendar      │ D08
├─ prompts                │ D09 версии промпта
├─ meetings ◄─────────────┤ D01–D03, D10 транскрипт, D11/D12 draft и final, статус
│   ├─ meeting_tasks ─ task_owners   задачи и договорённости → D07
│   ├─ skill_events                  D13 события матрицы
│   └─ meeting_signals               наблюдения и сигналы
└─ pipeline_runs                     D17 время, токены, статус — без текста встречи
```
 
Решения:
- **ID — текстовые (E01, M01, load), а не UUID из техпроекта.** Те же ID, что в JSON-схеме выжимки и в эталоне, поэтому вывод модели пишется в БД без перевода. UUID остались у встреч и пунктов.
- **Исполнители — отдельной таблицей `task_owners` с внешним ключом.** Задача на двоих — две строки. Выдуманный исполнитель физически не сохранится.
- **`meetings` хранит выжимку дважды:** `summary_draft` (как ответила модель) и `summary_final` (как подтвердил руководитель). Статус `edited` = были правки. Отсюда онлайн-метрика «принято без правок» и новые эталоны (D12).
- **`UNIQUE (tg_chat_id, tg_message_id)`** — повторная отправка того же голосового не создаст вторую встречу (D02).
- **ПДн в схеме `pii`.** Позже можно выдать роли n8n доступ к `app`, а к `pii` — только узлу псевдонимизации.
## Функции
 
| Функция | Что делает |
| --- | --- |
| `app.wd_add(дата, N)` | Дата через N рабочих дней с учётом праздников: `wd_add('2026-11-03', 1)` = 05.11 |
| `app.prompt_context(дата)` | Весь контекст на дату встречи одним JSON: команда в составе на эту дату, навыки, недели с пометкой нерабочих дней, +1/2/3/5/10 рабочих дней, концы месяцев, текущий и следующий спринт, праздники на 6 недель, карта псевдонимизации |
| `app.save_summary(meeting_id, json, 'draft' / 'final')` | Сохраняет выжимку по контракту schema_version 1.0. `draft` — только JSON в `summary_draft`; `final` — JSON и все пункты. Проверяет ID сотрудников и навыков, `kind`, `due.type`, формат дат. Повторный `final` пересобирает пункты без дублей |
| `app.v_open_tasks` | Открытые задачи из подтверждённых встреч, с исполнителями и признаком просрочки (D07, для /brief) |
| `app.v_skill_matrix` | Уровень по последнему снимку и число ↑/↓ из встреч после него (D06 + D13) |
| `app.v_runs_daily` | Запуски по дням: успешные, p95 задержки, токены (D17) |
 
Ошибки `save_summary` сформулированы для модели, их можно отдать ей при повторе как есть. Например: «Неизвестные employee_id: HR. Используй только ID из состава команды, остальные имена — в unresolved.unknown_names» или «задача 1: due.value "25.09.2026" должен быть датой YYYY-MM-DD».
 
## Шаг 1. Кластер PostgreSQL в Amvera
 
1. Главная Amvera → создать **PostgreSQL**. Регион тот же, что у n8n (msk). Имя проекта, например, `mvp-db`.
2. Параметры: имя базы `assistant`, пользователь `assistant`, надёжный пароль (сохраните сразу), версия 16 или 17, 1 экземпляр, диск — минимальный (данных меньше 1 МБ). Расширения не нужны: pgvector понадобится позже, для RAG.
3. Тариф — минимальный. Стоимость посмотрите в интерфейсе и внесите в учёт бюджета проекта.
4. После запуска откройте страницу «Инфо» кластера и скопируйте **внутреннее доменное имя для чтения/записи**. Вид: `amvera-<ваш логин>-cnpg-mvp-db-rw`. Внешний домен не создавайте: n8n в той же сети Amvera, и база не будет видна из интернета.
## Шаг 2. Подключение n8n
 
n8n → Credentials → Add → **Postgres**:
 
| Поле | Значение |
| --- | --- |
| Host | `amvera-<логин>-cnpg-mvp-db-rw` |
| Database | `assistant` |
| User / Password | из шага 1 |
| Port | 5432 |
| SSL | Disable (трафик внутри сети Amvera). Если n8n не подключится — Allow |
 
Имя credential: «Postgres ИИ-ассистент». Нажмите Test — должно быть «Connection tested successfully».
 
## Шаг 3. Установка схемы и справочников
 
1. n8n → Import from File → `n8n/e03_setup_db.workflow.json`.
2. В каждом из четырёх узлов Postgres выберите credential «Postgres ИИ-ассистент».
3. Execute workflow. В узле «4. Проверка» должно быть:
| Поле | Ожидается |
| --- | --- |
| employees_10 … sprints_52 | 10, 231, 8, 75, 64, 247, 52 (число в названии поля) |
| after_0311_is_0511 | 2026-11-05 |
| sprint_1609_is_S2026_19 | S2026-19 |
| migrations | 001_schema, 002_seed_testlab, 003_functions |
 
Повторный запуск безопасен. Так же обновляются справочники: правка в `gen.py` → новый `02_seed.sql` → вставить в узел «2. Справочники» → запустить.
 
## Шаг 4. Контекст для промпта (перенесён в v6)
 
Скопируйте содержимое `n8n/prompt_context_nodes.json` и вставьте на холст основного workflow (Ctrl+V). Появятся два связанных узла:
- **«Справочники: контекст»** (Postgres): `SELECT app.prompt_context($1::date)`, параметр — `{{ $json.meeting_date }}`. Выберите credential.
- **«Собрать контекст для промпта»** (Code). В константе `MEETING_NODE` — имя узла, где у вас лежит `meeting_date`.
Подключите их после получения даты встречи и до GigaChat. В промпт v4 вставьте `{{ $json.context_text }}` перед транскриптом. Шесть узлов Data table из прошлой версии больше не нужны.
 
## Workflow v5 (e03, часть 2) — готов
 
Основной workflow переведён на PostgreSQL: дата встречи (подпись или кнопки), состояние бота в `app.chat_state`, журнал запусков с токенами. Промпт v3 без изменений. Миграция базы — `sql/04_v5_bot.sql` (входит в workflow установки, узел «4. Миграция v5»). Инструкция по переключению и план проверки — `n8n/v5/README_v5.md`.
 
Шаг 4 выше (контекст из базы в промпте) переносится в **v6** вместе с промптом v4 и схемой выжимки 1.0: в v3 команда и навыки записаны в самом промпте, и контекст из базы к нему не подходит.
 
## Решения, которые стоит подтвердить
 
1. **Старая таблица «Выжимки 1:1» не переносится.** Там тестовые прогоны в формате до схемы 1.0. Предлагаю выгрузить её в CSV (Data tables → ⋯ → Download CSV) и положить в архив проекта.
2. **Внутренняя БД самой n8n остаётся SQLite.** Перевод n8n на PostgreSQL решает подвисания «Database ping timed out», но это отдельная операция: экспорт и импорт workflow и credentials, потеря истории запусков и Data tables. Предлагаю отдельной задачей после переключения основного workflow, в той же базе Amvera, но в отдельной схеме или базе `n8n`.
3. **Уровни матрицы (D06)** записаны снимком на 01.09.2026, до сентябрьских встреч. Тогда ↑/↓ из встреч 14–25.09 видны в `v_skill_matrix` как изменения после снимка.
