# Конвейер разработки по ролям — уровень 1 (роли вручную)

Каждая задача с кодом проходит одни и те же шаги. Роли исполняют разные модели, человек утверждает спецификацию и результат.

## Роли

| Роль | Кто | Что делает | Результат |
| --- | --- | --- | --- |
| Аналитик | Claude | Пишет спецификацию по `spec_template.md` | `docs/specs/<задача>.md`, статус «черновик» |
| Владелец задачи | Человек | Читает спецификацию, задаёт вопросы, утверждает | Статус «утверждена» |
| Разработчик | GigaCode | Пишет код строго по утверждённой спецификации | Код в `src/` |
| Ревьюер кода | Claude | Проверяет код по `review_checklist.md` | Список замечаний с серьёзностью |
| Тестировщик | Claude | Пишет тесты по критериям приёмки, не глядя в код | Тесты в `tests/` |
| Запуск и приёмка | Человек | Запускает `pytest`, принимает результат | Строка в `pipeline_log.csv` |

## Порядок

1. Спецификация → вопросы → утверждение человеком.
2. Тесты по критериям приёмки (пишутся до кода или параллельно с ним).
3. Код от GigaCode по спецификации.
4. Первый запуск тестов — результат фиксируется в журнале до любых правок.
5. Ревью кода по чек-листу.
6. Доработка: замечания ревью и упавшие тесты → GigaCode. Не больше 3 кругов.
7. Приёмка человеком, коммит, строка в журнале.

## Правила

- Ревьюер и разработчик — разные модели.
- Тесты реально запускаются; «выглядит правильно» проверкой не считается.
- Тесты пишутся по спецификации, а не по готовому коду.
- Спецификацию после утверждения меняют только новой версией (v1 → v2) с записью причины.
- Если после 3 кругов тесты не проходят — остановка и разбор: проблема в спецификации, в задаче или в инструменте.
- Секреты (ключи, пароли) в чат с моделями и в репозиторий не попадают.

## Журнал `pipeline_log.csv`

Одна строка — одна задача. Заполняется в день закрытия задачи.

| Поле | Что писать |
| --- | --- |
| `date` | Дата закрытия, ГГГГ-ММ-ДД |
| `task` | Короткое название задачи |
| `spec_version` | Версия спецификации, по которой принят код (1, 2…) |
| `spec_questions` | Сколько вопросов и правок было к черновику спецификации |
| `tests_total` | Сколько тестов в наборе |
| `tests_failed_first_run` | Сколько упало при первом запуске |
| `passed_first_run` | `yes`, если при первом запуске прошли все тесты, иначе `no` |
| `rework_rounds` | Сколько кругов доработки понадобилось (0–3) |
| `defects_review` | Дефекты, найденные ревью кода |
| `defects_tests_only` | Дефекты, которые нашли только тесты (ревью пропустило) |
| `defects_human` | Дефекты, которые нашёл человек после ревью и тестов |
| `min_spec`, `min_code`, `min_review`, `min_tests`, `min_rework` | Время по шагам, минуты |
| `tokens_claude` | Токены Claude за задачу, если известны |
| `accepted` | `yes` / `no` |
| `notes` | Что пошло не так и что поменять в шаблонах |

## Метрики (считаются по журналу)

- Доля задач, прошедших тесты с первого раза: `passed_first_run = yes` / все задачи.
- Среднее число кругов доработки.
- Доля дефектов, пойманных ревью: `defects_review` / (`defects_review` + `defects_tests_only` + `defects_human`).
- Время на задачу и его распределение по шагам.
