# Шаг 2.2. Данные ИИ-ассистента руководителя: состав, источники, форматы
 
11.11.2026, обновлено 12.11.2026 · Юлия Короткова · живая версия: https://claude.ai/artifact/27mjfynB6T3NomdMHuLmC6
 
## 1. Рамка этапа
 
Мы не обучаем модель: GigaAM и GigaChat готовые. Поэтому этап 2.2 у нас — это подготовка трёх видов данных: контекст для промпта (справочники), рабочий поток (аудио → выжимка) и оценочный набор с эталонами.
 
**Границы.** Берём MVP — сценарий A «Голосовые 1:1» (подпроцессы 4.1–4.3) и то, без чего он не работает: состав команды и матрицу навыков. ИПР-квесты, психотипы, ДИ, вакансии и ачивки — следующие итерации, их данные разберём, когда дойдём до них. Все данные в проекте синтетические (команда «ТестЛаб» придумана), реальных ПДн нет.
 
**Как положения руководства переносятся на LLM-ассистента:**
 
| Положение руководства | Как применяем у себя |
| --- | --- |
| Обучающая, валидационная и тестовая выборки | Обучения нет. Вместо этого: пул примеров для промпта, рабочий набор для настройки промпта и отложенный тест (раздел 5) |
| Историческая глубина 2–3 года | Не нужна: у встреч 1:1 нет сезонности. Нужна репрезентативность: разные сотрудники, темы, голоса, качество звука |
| Баланс классов | Аналог — доля сложных случаев: задача без срока, относительный срок, задача на двоих, неявный исполнитель |
| Эталон (Gold Standard) | Эталонные транскрипты (сценарии) и эталонные выжимки |
| Обезличивание до обучения | Важнее до вызова внешнего API: транскрипт уходит в GigaChat (раздел 6) |
| Версионирование DVC | Тексты (промпт, эталоны, разметка) — в Git; аудио — в хранилище, с хэшем в реестре |
| Контракты данных, Pydantic | JSON-схема выжимки и её проверка в n8n до сохранения (раздел 4) |
 
## 2. Карта данных
 
Ассистенту нужны 17 видов данных. На 11.11 в MVP не было пяти из них (D05, D07, D08, D13, D17), ещё шесть были частично. Именно отсюда приходят ошибки, которые мы видим в эталонах: сроки без даты встречи, навыки вне матрицы, связи с прошлыми встречами. Колонка «В MVP сейчас» обновлена 12.11 после перехода на PostgreSQL (e03) и workflow v5.
 
Схема потока (в живой версии — рисунок «Справочники и прошлые встречи входят в каждую выжимку»):
Голосовое (D01–D03, Telegram) → GigaAM-v3 (распознавание) → Транскрипт (D10) → GigaChat-2-Max (извлечение пунктов) ← Контекст для промпта (D03 дата встречи, D04 состав команды, D05 навыки, D06 уровни, D07 прошлые задачи, D08 календарь, D09 промпт и примеры) → Выжимка JSON (D11) → Подтвердить или исправить (D12) → Хранилище (D07, D13, PostgreSQL). Оценка — отдельно от рабочего потока: эталонные транскрипты (D14, WER/CER) сравниваются с транскриптом, эталонные выжимки (D15, P/R/F1) — с выжимкой, всё сводится в журнал качества (D16).

**Решение по D03 (11.11.2026, уточнено 12.11.2026).** Бот ищет дату встречи во фразе про встречу в начале записи («Встреча с Павлом четырнадцатого сентября», «Вчера была встреча с Марией», «Встреча в понедельник…»). Если нашёл — пишет «Дата встречи — … (из записи)» с кнопкой «Изменить дату» и сразу делает выжимку; дату можно сменить до подтверждения, выжимка пересчитается. Если не нашёл — спрашивает «Когда была встреча?» с кнопками «Сегодня», «Вчера», «Другая дата» (ввод ДД.ММ или «вчера»). Распознавание запускается сразу, GigaChat — после выбора даты.
 
Почему не подпись к голосовому: голосовому, записанному кнопкой микрофона в Telegram, подпись добавить нельзя. Подпись «14.09» работает только для загруженных аудиофайлов (источник `caption`).
 
Открытые детали:
 
- Руководитель не ответил на вопрос о дате: встреча ждёт в статусе `awaiting_date`. Автоподстановку даты сообщения через 30 минут с пометкой «дата встречи не подтверждена» можно добавить отдельно.
- Прогоны оценочного набора: запись начинается с даты из сценария («Встреча с Иваном Петровым четырнадцатого сентября…»), бот не спрашивает дату.
- Источник даты хранится в `meeting_date_source` = speech, button, caption или message_date. Доля встреч, где дату из речи пришлось менять, — метрика качества распознавания даты.

## 4. Форматы и схемы
 
Главное решение раздела — жёсткая JSON-схема выжимки. В ней исполнители и навыки ссылаются на ID из справочников, срок разложен на тип и значение, а у каждого пункта есть цитата из транскрипта. Тогда половину проверок качества можно делать кодом, без LLM-судьи.
 
**Аудио (D01).** Telegram отдаёт голосовые в OGG/Opus. Имя файла в хранилище: `<message_id>.ogg`, в реестре — SHA-256 файла, длительность в секундах, дата получения. Стоит проверить, в каком месте сервис GigaAM приводит звук к своему формату и что делает с записями длиннее лимита. С v5.2 файл хранится в `app.meeting_audio` (3 месяца), SHA-256 считает база; дополнительно сохраняется `file_unique_id` Telegram.
 
**Состав команды (D04)**, одна строка на сотрудника, варианты имени через «;». Итоговый справочник — `employees.csv` (ID совпадают с номерами записей: E01 Иван, E02 Павел … E08 Алексей; M01 Татьяна до 31.10, M02 Александр с 01.11). Пример формата:
 
```csv
employee_id,full_name,aliases,role,grade,manager_id
E01,Иван Петров,Иван;Ваня;Петров,Инженер по тестированию,Junior,M01
E02,Павел Смирнов,Павел;Паша;Смирнов,Инженер по нагрузочному тестированию,Senior,M01
M01,Татьяна,Татьяна;я,Тимлид QA,Lead,
```
 
«я» в вариантах руководителя нужно, чтобы «я сама поговорю» становилось задачей Татьяны.
 
**Справочник навыков (D05)**, одна строка на колонку матрицы (итоговый — `skills.csv` и `skill_aliases.csv`):
 
```csv
skill_id,name,aliases
test_design,Тест-дизайн,тест-кейсы;техники тест-дизайна
func_regress,Функц. и регресс,регресс;регрессионная модель;ручное тестирование
api,API,API-тесты;контрактные тесты;Postman
ui_auto,UI-автотесты,Playwright;Selenium;UI-автоматизация
python,Python,pytest;курс Python
cicd,CI/CD,GitLab CI;пайплайн;мерж-реквест
load,Нагрузка,нагрузочное тестирование;k6;нагрузочный стенд
mobile,Мобильное,iOS;Android;мобильный регресс
```
 
**Выжимка (D11)** — контракт между GigaChat и остальной системой. Пример по записи 2:
 
```json
{
  "schema_version": "1.0",
  "meeting": {"employee_id": "E02", "manager_id": "M01", "meeting_date": "2026-09-15", "message_id": 1002, "prompt_version": "v4"},
  "tasks": [
    {"kind": "task", "owner_ids": ["E02"], "what": "Подготовить профиль нагрузки к релизу ЗаказПро 5.0",
     "due": {"type": "date", "value": "2026-09-25", "said": "до двадцать пятого сентября"},
     "evidence": "Павел готовит профиль нагрузки до двадцать пятого сентября"},
    {"kind": "task", "owner_ids": ["E02"], "what": "Написать инструкцию по нагрузочному стенду",
     "due": {"type": "none", "value": null, "said": "срок пока не поставили"},
     "evidence": "Договорились, что он запишет инструкцию, но срок пока не поставили"}
  ],
  "skills": [
    {"employee_id": "E02", "skill_id": "load", "direction": "up", "evidence": "Экспертиза по нагрузке … очень сильная"}
  ],
  "observations": [
    {"employee_id": "E02", "text": "Сильная экспертиза в архитектуре автотестов", "direction": "up", "evidence": "…и архитектуре автотестов у него очень сильная"}
  ],
  "signals": [
    {"type": "attrition_risk", "text": "Пишут рекрутеры, задумывается", "evidence": "ему постоянно пишут рекрутеры … задумывается"}
  ],
  "unresolved": {"unknown_names": [], "ambiguous_dates": []}
}
```
 
Правила полей:
 
- `kind`: task (разовая, со сроком) или agreement (долгосрочная: «каждую неделю», «если застряла — пишет»).
- `due.type`: date, range («на следующей неделе» → две даты), from («с 28.09»), event («на следующей встрече»), recurring, none. Поле `said` хранит слова руководителя — по нему проверяем пересчёт.
- Даты в JSON — ISO (2026-09-25), в сообщении бота — ДД.ММ.ГГГГ. Проверку «Даты ДД.ММ.ГГГГ» в разметке e46 после перехода на схему переименуем в «Даты в ISO».
- `owner_ids` и `skill_id` — только из справочников. Имя, которого нет в составе команды, идёт в `unresolved.unknown_names`, а не выдумывается.
- `evidence` — дословный фрагмент транскрипта. Если фрагмента нет в тексте (проверка нечётким поиском), пункт помечается как возможно выдуманный. Это дешёвая проверка Faithfulness.
- `signals.type` — закрытый список: attrition_risk, burnout, motivation, goal, conflict, mood, probation, other.
- Категории полей совпадают с группами в эталоне e46: задачи и договорённости, навыки матрицы, наблюдения, сигналы. Так разметка и вывод бота сравниваются построчно.
Режим LLM_JSON_MODE сейчас выключен, поэтому перед сохранением нужна проверка схемы. Она уже есть в базе: функция `app.save_summary` проверяет ID сотрудников и навыков, `kind`, `due.type` и формат дат и возвращает ошибку текстом, понятным модели. Подключение — в workflow v6: невалидный ответ — повтор с текстом ошибки, после второй неудачи — сообщение руководителю.
 
## 5. Датасеты
 
Из 100 записей 73 идут в рабочий набор, 27 — в отложенный тест. Примеры для промпта живут отдельно и в оценке не участвуют. Так мы видим ошибки на рабочем наборе и честно проверяем промпт на записях, под которые его не подгоняли.
 
| Набор | Размер | Для чего | Правило |
| --- | --- | --- | --- |
| Примеры для промпта | 3–5 синтетических текстов | Показать модели формат и сложные случаи | Пишутся отдельно, не из 100 записей; персонажи не из «ТестЛаб» |
| Рабочий набор | 73: записи 1–10, по 14 из четырёх батчей по 20 и 7 из последних 10 | Разбор ошибок, правки промпта, еженедельные метрики | Смотрим каждую ошибку |
| Отложенный тест | 27: по 6 из четырёх батчей по 20 и 3 из последних 10 | Итоговая оценка версии промпта | Только считаем метрики, на контрольных точках; тексты ошибок не читаем |
 
Записи 1–10 уже видели и под них дорабатывали промпт v3, поэтому в тест они попасть не могут. Выбор 6 записей в тест делаем до прогона батча и случайно внутри каждого вида встреч (стратификация). Записи с секвенцией (встречи 1 и 9 с Иваном) держим в одном наборе — иначе тест подскажет ответ.
 
**Покрытие.** Вместо баланса классов следим, чтобы каждый сложный случай встречался не реже определённого числа раз. Цели на 100 записей — моё предложение, скорректируйте.
 
| Случай | В записях 1–10 | Цель на 100 |
| --- | --- | --- |
| Задача без срока | 2 (записи 2, 10) | ≥ 10 |
| Срок-событие («на следующей встрече», «к встрече втроём») | 2 (записи 4, 5) | ≥ 8 |
| Относительный срок («до пятницы», «через две недели») | во всех 10 | в большинстве |
| Задача на двоих и более | 3 (записи 3, 4, 10) | ≥ 10 |

## 6. Персональные данные
 
В учебном проекте данные синтетические. В реальной компании голосовые 1:1 содержат чувствительные сведения о сотрудниках, и контур нужно спроектировать так, будто данные настоящие. Раздел описывает инженерные меры. Правовые вопросы (основание обработки, уведомление сотрудников, договор с провайдером LLM) решаются с юристом.
 
**Что чувствительного встречается даже в 10 сценариях:** ФИО, запрос пересмотра зарплаты (запись 4), усталость и риск выгорания (записи 2, 3), риск ухода (записи 2, 10), итоги испытательного срока (запись 8), отказ от психологического теста (запись 6), конфликт коллег (записи 4, 5). Руководитель может случайно упомянуть и здоровье сотрудника — это специальная категория ПДн.
 
**Куда уходят данные:**
 
| Участок | Что передаётся | Риск | Мера |
| --- | --- | --- | --- |
| Телефон → Telegram | Аудио целиком | Инфраструктура мессенджера вне контроля компании | Для пилота — синтетика; для промышленной версии — оценить корпоративный мессенджер или веб-форму |
| Amvera (n8n, GigaAM, PostgreSQL) | Аудио, транскрипт, выжимка | Хранение дольше нужного | Аудио — 3 месяца, затем автоматическое удаление (решение 12.11); логи n8n чистятся через 72 ч |
| n8n → GigaChat API | Транскрипт и список команды | Текст с именами у внешнего вендора | Имена заменяются на метки перед вызовом (решение 12.11, с v6); условия хранения запросов — в договоре |
| Хранилище ассистента | Всё перечисленное | Доступ посторонних | ФИО и формы имён — в отдельной схеме `pii`, рабочие данные — в `app`; доступ только руководителю своей команды |
| Оценочный набор | Аудио, эталоны | Реальные записи попадут в тесты и Git | В набор — только синтетика или обезличенные тексты с согласия; аудио не кладём в Git |
 
**Решение по ПДн (12.11.2026).**
 
1. **Имена заменяются на метки перед GigaChat.** После распознавания все формы имён сотрудников, работающих на дату встречи, заменяются на метки («с Иваном Петровым» → «с [E01]»). Модель получает команду без ФИО: ID, должность, направление (`app.prompt_context_pseudo`). Имена подставляются обратно уже в n8n, в сообщении руководителю. В базе транскрипт хранится как есть: это наш контур. Подключение — в workflow v6 вместе с промптом v4: промпт v3 перечисляет команду по именам и возвращает имена, поэтому в v5 метки сломали бы базовую линию для сравнения. Код замены готов и проверен на сценариях (`n8n/v6/pseudonymize.js`): падежи, уменьшительные, ё/е, полные имена целиком; слова вроде «Ванильный» и «Иванова» не трогаются.
   Ограничения: имя, искажённое при распознавании («Еле» вместо «Елене»), не заменится и уйдёт в GigaChat как есть — нужен нечёткий поиск (задача x05); «Петрова» всегда становится [E01], даже если речь о человеке вне команды. Эксперимент «F1 по исполнителям с метками и без» остаётся в PoC как проверка, что метки не ухудшают качество.
2. **Аудио хранится 3 месяца.** Файл голосового сохраняется в `app.meeting_audio` вместе с SHA-256; через 3 месяца его удаляет ежедневный workflow «Очистка аудио встреч», во встрече остаются хэш, длительность, транскрипт и отметка `audio_deleted_at`. Копия у Telegram от нас не зависит — для промышленной версии это аргумент за корпоративный канал (раздел выше). Срок хранения транскриптов и выжимок отдельно не ограничен.
**Минимизация.** Сигналы о здоровье и личной жизни ассистент не должен сохранять как факт. В промпте нужно правило «не фиксировать диагнозы и личные обстоятельства», а в оценочном наборе — 2–3 записи, на которых это правило проверяется.
 
## 7. Риски качества данных
 
Самый серьёзный риск для оценки — однородность набора. Сценарии написаны чистым языком и начитаны, если не ошибаюсь, одним голосом. Результат «10 из 10» на таких данных переоценивает поведение на живой речи.
 
| Риск | Как проявится | Мера |
| --- | --- | --- |
| Однородный набор (один голос, написанная речь) | Хорошие метрики, плохая работа у другого руководителя | Цели покрытия из раздела 5: другие дикторы, шум, самоисправления; часть записей — свободная речь по тезисам, а не чтение |
| Ошибки распознавания в именах и терминах | Неверный исполнитель, потерянный навык | Варианты имён и синонимы навыков в справочниках; нечёткое сопоставление после распознавания; WER и точность ключевых слов (задача q02) |
| Нет даты встречи или дата сообщения другая | Все относительные сроки съезжают | Дата встречи — обязательное поле входа: из речи, иначе кнопки; «Изменить дату» до подтверждения; поле `said` для проверки пересчёта |
| Дата из речи распознана неверно (например, срок задачи принят за дату встречи) | Сроки посчитаны от неверной даты | Дата ищется только во фразе про встречу, сроки с «до/к/по» исключаются; бот показывает найденную дату с кнопкой «Изменить дату»; считаем долю смен даты |
| Справочник навыков расходится с речью | Навыки вне матрицы или дубли («Python» и «pytest») | Таблица синонимов; отдельный блок «Наблюдения» для того, что в матрицу не входит |
| Ошибка в эталоне | Модель штрафуется за правильный ответ (как «холодный старт» в старом эталоне 6) | Источник ошибки «Эталон» в разметке; повторная разметка 15 записей и каппа Коэна |
| Утечка теста в промпт | Завышенные метрики | Пулы из раздела 5; примеры для промпта с другими персонажами |
| Зависимость от прошлых встреч | «Как и решили» нечем разрешить | Пока — правило сопоставления; после v6 — открытые задачи сотрудника в контексте (D07, `app.v_open_tasks`) |
| Инструкции в самой речи («игнорируй правила…») | Модель меняет поведение | Транскрипт передаётся как данные в размеченном блоке; 2–3 такие записи в наборе (курс Red Teaming) |
| Нет лога успешных запусков | Нельзя посчитать задержку и стоимость | Закрыто: `app.pipeline_runs` (время распознавания, время LLM, токены, статус — без текста встречи) |
| Правки руководителя не сохраняются как разница | Нет онлайн-метрики и источника новых эталонов | Закрыто: `summary_draft` и `summary_final` (D12) |
