# Схема выжимки 1.0: решения и правки

13.11.2026, правки 14.11.2026 · ИИ-ассистент руководителя, шаг 2.2 · задача «JSON-схема выжимки 1.0 + промпт v4 + проверка схемы в n8n»

Схема утверждена 13.11.2026. Файл контракта — `summary_schema_1.0.json` (JSON Schema 2020-12), кладётся в Git рядом с эталонами. Этот документ заменяет раздел 4 «Шаг 2.2» в части формата выжимки: там остался пример до решений ниже.

## Решения

| # | Вопрос | Решение |
| --- | --- | --- |
| 1 | Кто заполняет блок `meeting` | Модель возвращает только `employee_id` (можно `null`, если сотрудника определить не удалось). `meeting_date`, `manager_id`, `message_id`, `prompt_version` дописывает n8n после ответа модели и до проверки |
| 2 | Формат срока | Поля `value` и `value_to`. Просрочка: для `date` по `value`, для `range` по `value_to`; остальные типы не просрочиваются |
| 2а | Повторяющаяся договорённость без срока | `kind: agreement`, `due.type: recurring`, `value` и `value_to` пустые, периодичность — словами руководителя в `said` («раз в неделю по часу»). Если названы начало или конец — они в `value` и `value_to`. В `owner_ids` — все участники (ментор и подопечный) |
| 3 | Направление у навыков | Три значения: `same` — текущий уровень, `up` — улучшение, `down` — ухудшение. `up` и `down` только при словах об изменении. При `same` — необязательное поле `assessment`: `strong` / `weak`. Направление — это слова руководителя, а не изменение уровня в матрице (см. раздел ниже) |
| 4 | Закрытые списки | `kind` и `due.type` без изменений. В `signals.type` добавлен `achievement`. У сигнала обязательное поле `tone`: `risk` / `positive` / `neutral`. `neutral` — факт без оценки («отказалась от психологического теста»), добавлен 14.11.2026 |
| 5 | Что такое `skill_id` | Тема из словаря тем (`app.topics`), а не компетенция матрицы. У темы записана компетенция в каждом треке. Перевод события в компетенцию по треку сотрудника и решение «тема без компетенции в треке — наблюдение» — в задаче «Матрица компетенций в базе» (21.11): там появятся компетенции и треки сотрудников |
| 6 | Направления развития | «Тест-аналитик» — не навык, а целевой профиль: уровни 3–4 по компетенциям блоков B и C. Хранится в `app.development_paths`. Упоминание в речи («хочет развиваться в тест-аналитику») модель пишет в `signals` с `type = goal` |
| 7 | Обновления задач с прошлых встреч (14.11.2026) | Отдельный блок `task_updates`, новые задачи в нём не пишутся. Модель выбирает `task_id` из списка открытых задач в контексте (T и номер); не нашла или подходят несколько — `null`, руководитель привяжет при «Исправить». Статусы: `in_progress`, `done`, `cancelled`, `rescheduled`; новый срок `due` — только при `rescheduled` |

## Обновления задач (решение 7)

Пример из записи 10: «Профиль нагрузки для релиза готов» — это не навык и не новая задача, а выполнение задачи 02-T1 со встречи 15.09.

```json
"task_updates": [
  {"task_id": "T7", "what": "Профиль нагрузки к релизу 5.0", "status": "done", "due": null,
   "evidence": "Профиль нагрузки для релиза готов"},
  {"task_id": "T8", "what": "Инструкция по нагрузочному стенду", "status": "rescheduled",
   "due": {"type": "date", "value": "2026-10-16", "value_to": null, "said": "до шестнадцатого октября"},
   "evidence": "Инструкцию по нагрузочному стенду Павел напишет до шестнадцатого октября"}
]
```

- **Откуда модель знает ID.** n8n передаёт в контекст открытые задачи всей команды с прошлых подтверждённых встреч: ID, формулировка, исполнители, срок, статус. Команда небольшая, поэтому список не фильтруется по сотруднику: на встрече могут отчитаться и по задачам руководителя.
- **Как база применяет обновление.** Статус задачи берётся из последнего обновления с подтверждённых встреч; новый срок — из последнего переноса, исходный срок не затирается. Черновик выжимки задачи не меняет — только подтверждение. Правка и повторное подтверждение встречи пересчитывают статусы.
- **Что база отклоняет.** ID, которого нет среди задач прошлых подтверждённых встреч; ссылку на задачу этой же встречи; срок при статусе, отличном от `rescheduled`.
- **Имена в контексте.** Формулировки задач могут содержать имена, поэтому блок открытых задач в v6 проходит псевдонимизацию вместе с транскриптом.

## Направление навыка и уровень в матрице (14.11.2026)

Вырос ли навык, можно узнать только сравнением с исходным уровнем сотрудника по компетенции. Поэтому это две разные вещи:

- **Направление в выжимке** (`same` / `up` / `down`) — что сказал руководитель: «уже получше», «просел», «уверенно». Модель уровней не видит и ничего не сравнивает.
- **Изменение уровня в матрице** — решение по накопленным событиям относительно исходного уровня. Исходные уровни 8 сотрудников по 29 компетенциям заполняются в задаче «Матрица компетенций в базе» (21.11). Прежняя таблица `app.skill_levels` была по 8 старым навыкам и очищена миграцией 007. До 21.11 события копятся в `skill_events`, но в изменение уровня не превращаются. Новый уровень подтверждает руководитель.

## Навыки и матрица компетенций (решение 5)

Источник навыков — актуальная матрица `qa-competency-matrix.xlsx` из репозитория `qailab-materials`: 29 компетенций (трудовые функции профстандартов 06.004 и 06.016), три трека и управление, 16 грейдов, шкала 0–5. Прежний справочник из 8 навыков демо-данных отменён.

Почему тема, а не компетенция. Руководитель говорит «Python», «Playwright», «k6», а в матрице компетенции называются «Определение и описание тестовых случаев», «Проведение тестирования ПО». Привязка «Playwright → B.1 в треке автоматизации» записана в матрице, в описаниях уровней, поэтому хранится таблицей, а не угадывается моделью.

- Модель выбирает `skill_id` из словаря тем (43 темы).
- Уровень 0–5 ставит руководитель. Встречи дают только события (`same` / `up` / `down`, `strong` / `weak`) с цитатой; изменение уровня подтверждает человек.
- Схему 1.0 это не меняет: `skill_id` в ней — строка, список в схему не зашит.

Матрица разобрана в CSV скриптом `parse_matrix.py`: `competencies.csv` (29), `grades.csv` (16), `grade_requirements.csv` (464), `level_descriptions.csv` (224 утверждения, каждое привязано к компетенции или помечено «доп.»), `scale.csv`, `matrix_version.csv` (SHA-256 файла). Загрузка в базу, уровни сотрудников и представление с разрывами — отдельная задача в плане на 21.11 «Матрица компетенций в базе».

### Мобильное тестирование в матрице (13.11.2026)

В матрице не было мобильного тестирования. Решение: четвёртый трек не заводить, а добавить знания и навыки внутрь листов «Ручное» (8 строк, уровни 1–4) и «Автоматизированное» (4 строки, уровни 2–4). Каждая строка начинается словами «Для мобильных продуктов:» и привязана к трудовой функции, как остальные. Листы «Грейды» и «Оценка сотрудника» не менялись. Строки вносит скрипт `add_mobile.py`. В той же версии на листах треков снята фиксированная высота строк блоков C–E. В CSV разобрана эта версия файла (SHA-256 начинается с `206f5083`). Файл нужно загрузить в репозиторий и на сайт.

## Что добавлено сверх решений

Эти правила я внесла сама, чтобы схема и база были согласованными. Их можно отменить.

- **Наблюдения оцениваются так же, как навыки:** `direction` = `up` / `down` / `same` и `assessment` при `same`. Отличие одно: у наблюдения `direction` может быть `null` («перешёл на новый проект»).
- **`owner_ids` может быть пустым массивом** — случай «исполнитель не назван» из плана покрытия.
- **Справочники в схему не зашиты.** Схема проверяет только вид ID (`E01`, `M01`, `load_testing`). Что такой сотрудник или тема существует, проверяет `app.save_summary` по таблицам.
- **Сотрудник встречи — не руководитель.** `meeting.employee_id` = `M01` база отклоняет.
- **Подтвердить выжимку без сотрудника встречи нельзя.** Черновик с `employee_id: null` сохраняется, подтверждение — нет.
